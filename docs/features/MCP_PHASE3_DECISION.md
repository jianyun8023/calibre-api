# MCP 阶段三决策 - 资源和提示功能暂缓

> **日期**: 2024-11-28  
> **决策**: 暂缓实现资源和提示功能  
> **原因**: 工具功能已足够满足需求

---

## 📋 决策背景

在完成阶段二（6个MCP工具）后，原计划继续实现阶段三：资源（Resources）和提示（Prompts）功能。

然而，在实际评估后，我们决定暂缓阶段三的实现。

---

## 🤔 为什么暂缓？

### 1. 工具功能已经足够

已实现的 **6 个 MCP 工具** 完全覆盖了核心使用场景：

| 工具 | 覆盖场景 |
|------|---------|
| `search_books` | 书籍搜索和发现 |
| `get_book` | 获取书籍详情 |
| `random_books` | 随机推荐 |
| `recent_books` | 最新内容 |
| `get_isbn_metadata` | ISBN 查询 |
| `search_metadata` | 在线元数据搜索 |

这些工具可以满足绝大多数用户需求，无需额外的资源和提示功能。

### 2. 资源功能可通过工具替代

原计划的资源功能：
- `book://{id}` → 可用 `get_book` 工具替代
- `book://{id}/cover` → 工具返回封面 URL
- `book://{id}/toc` → 可调用现有 REST API
- `search://{query}` → 可用 `search_books` 工具替代

**结论**: 资源功能不是必需的，工具已提供相同能力。

### 3. 提示功能的局限性

提示（Prompts）功能主要是为 AI 提供预定义的对话模板。

**问题**:
- 现代 AI 模型已经足够智能，不需要固定模板
- 用户可以直接用自然语言描述需求
- 提示模板反而限制了灵活性

**示例**:
- 不需要模板: "请搜索关于 Python 的书籍"
- 直接对话: "我想学 Python，有什么好书推荐？"

AI 可以理解第二种更自然的表达方式。

### 4. API 复杂度高

`mcp-go` 框架的资源和提示 API 相对复杂：
- 需要处理多种资源内容类型（Text, Blob, Embedded）
- 需要实现资源列表、读取、模板等多个接口
- 提示参数渲染需要额外的模板引擎

**投入产出比不高**: 实现复杂度高，但实际价值有限。

### 5. 保持简洁

遵循 KISS（Keep It Simple, Stupid）原则：
- 更少的代码 = 更少的 bug
- 更简单的 API = 更容易使用
- 更专注的功能 = 更好的体验

## 🎯 推荐使用方式

### 直接使用工具

**搜索书籍**:
```
用户: "帮我找关于 Python 的书"
AI: 调用 search_books(query="Python")
```

**获取详情**:
```
用户: "给我看看 ID 123 的书籍信息"
AI: 调用 get_book(id="123")
```

**随机推荐**:
```
用户: "推荐 5 本有趣的书"
AI: 调用 random_books(limit=5)
```

### 无需资源URI

**不需要**:
```
AI: 读取资源 book://123
```

**直接用工具**:
```
AI: 调用 get_book(id="123")
```

### 无需提示模板

**不需要**:
```
渲染提示: "请搜索关于 {topic} 的书籍"
填充参数: topic="Python"
```

**直接对话**:
```
用户: "我想学 Python，有什么书推荐？"
AI: 理解意图 → 调用 search_books
```

## 🔮 未来考虑

如果未来有以下需求，可以重新评估资源和提示功能：

### 可能需要资源的场景
1. **批量资源访问**: 需要一次性获取多个相关资源
2. **资源订阅**: 需要监听资源变化
3. **复杂资源关系**: 需要表达资源之间的层级关系

### 可能需要提示的场景
1. **标准化工作流**: 需要固定的交互模板
2. **新手引导**: 需要预定义的使用示例
3. **多语言支持**: 需要本地化的提示文本

**当前评估**: 这些场景都不是现在的需求。

## ✅ 决策总结

### 最终决定
**暂缓实现阶段三（资源和提示），专注于已完成的工具功能。**

1. ✅ 工具功能已足够满足需求

5. ✅ 遵循 KISS 原则

- ✅ 无负面影响：所有核心功能已完整
- ✅ 正面影响：代码更简洁，维护更容易
